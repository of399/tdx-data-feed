# M-4：三条 AST 语义守卫（原子写 / 吞错必计数 / 外部调用必带 timeout）

（2026-11-01 落地 · 工具 `scripts/ci_semantic_guard.py` · 基线 `config/semantic_baseline.json` · 趋势 `scripts/quality_trend.py`）

## 0. 定位：M-2 之后的下一层

M-2（增量阻断）解决的是"**通用 lint 规则**不许新增"：ruff 的 252 条存量被冻结成额度，新增行引入任何 ruff 违规即失败。

但台账里 29 条"无守卫"问题中，真正有杀伤力的那批**根本不是 ruff 能表达的语义问题**：

| 台账条目 | 问题 | ruff 能查吗 |
|---|---|---|
| KI-ATOMIC-001~004 | 写文件不原子，读者可能读到半截 | ❌ |
| KI-SILENT-001~002 | except 吞掉错误，不进统计 | ❌（BLE001 只看"是否盲捕"，不看"是否计数"）|
| KI-MCP-001 | MCP 子进程管道读无 timeout，永久阻塞 | ❌ |

M-4 用**三条 AST 语义守卫**补上这一层，把"规则级增量阻断"扩展为"**语义级增量阻断**"。

## 1. 守卫 1 · 原子写（SEM001）

### 检测范围（AST 判定，不是正则）

| 写法 | 是否命中 | 说明 |
|---|---|---|
| `path.write_text(...)` / `path.write_bytes(...)` | ✅ | 覆盖写入 |
| `df.to_csv(p)` / `to_parquet` / `to_json` / `to_excel` / `to_pickle` / `to_hdf` | ✅ | 第 1 个位置参数为路径时 |
| `open(p, "w")` / `"wb"` / `"w+"` | ✅ | 覆盖写入 |
| `open(p, "a")` 纯追加（无先读） | ❌ 放行 | POSIX `O_APPEND` 语义，短行写入不撕裂 |
| `open(p, "a")` 且同函数先读过同一路径 | ✅ | **读-改-写无锁 → 并发丢行**（KI-ATOMIC-003）|
| 写到 `.tmp` / `.part` / 变量名含 tmp/temp/part | ✅ 但**需同函数有 `os.replace`** | 只写 tmp 不落位 = 数据丢失 |
| 写到 `.tmp` + 同函数有 `os.replace`/`os.rename`/`shutil.move`/`Path.replace` | ❌ 放行 | 标准的"先写临时再落位" |

### 触发条件

- 扫描范围 = **在役代码**（排除 `_archive/` 已归档、`v5/` 已冻结研究线、`tests/` 测试夹具、构建产物）；文件清单与 ruff 对齐（`ruff check . --show-files`）。
- 每个**函数**独立分析：模块级语句视为一个伪函数；嵌套函数各自独立，避免同一写入被重复计数。

### 命中后的处理行为

| 情形 | 行为 |
|---|---|
| CI（PR）| 门禁失败（退出码 1），打印 `文件:行号 · SEM001 · 基线 → 当前 · 证据` |
| CI（push main）| 基线断言失败（净增长） |
| 本地 | `make lint-gate` 复现；`make lint-semantic` 看明细 |
| 豁免 | `# noqa: SEM001 (理由)` —— **必须带理由**，无理由的 noqa 无效 |
| 修复 | 改成 `.tmp` + `os.replace`；随后 `make lint-baseline` 收紧基线（只降不升）|

## 2. 守卫 2 · 吞错必计数（SEM002）

### 检测范围

所有 `except` handler，按"是否吞错"与"是否计入统计"两维度判定：

| except 体 | 判定 | 提示 |
|---|---|---|
| 含 `raise` | ✅ 放行 | 错误向上传播 |
| 递增失败计数（`failed_count += 1`、`metrics['x'] += 1`、`error_cnt += 1`）| ✅ 放行 | 计入统计 |
| 调用计数函数（`record_error()` / `count_failure()` / `incr()` / `track_error()` …）| ✅ 放行 | 计入统计 |
| 登记进失败清单（`failures.append(e)` / `errors.add(x)`）| ✅ 放行 | 计入统计 |
| 仅 `pass` | ❌ | "错误完全不可追溯" |
| 仅文档字符串 | ❌ | 同上 |
| `continue` / `break` | ❌ | "失败被跳过且未计数" |
| 仅 `logger.exception(...)` | ❌ | **"已记录未计数"：统计口径缺失** |
| 其它 | ❌ | "既未 raise 也未递增失败计数" |

> 关键设计：**记日志 ≠ 计入统计**。日志是给人看的，统计是给机器看的——只有后者的缺失才会让"失败率"这个指标失真。

### 触发条件与处理行为

同 SEM001。豁免写法：`# noqa: SEM002 (best-effort 清理，已复核)`。

**这条守卫同时废掉了 ruff 的 BLE001 目录级豁免**（KI-RULE-001）：以前 `ruff.toml` 里对 `scripts/`、`tdxfeed/` 整目录豁免 BLE001，新代码盲吞错完全合法；现在新增行的盲吞错会被 SEM002 拦下——**存量豁免保留，新增不再豁免**。

## 4. 与现有门禁的集成方式

### 4.1 双维度基线（关键设计）

M-2 的门禁原本只有 **ruff 维度**。M-4 引入 **semantic 维度**，两者**基线文件独立、判定独立、审批独立**：

| 维度 | 基线文件 | 覆盖 |
|---|---|---|
| ruff | `config/ruff_baseline.json` | 252 条 / 82 文件 / 31 规则 |
| semantic | `config/semantic_baseline.json` | 570 条 / 184 文件 / 3 规则 |

> **为什么要独立基线**：如果把 SEM 码塞进同一个基线，首次引入 570 条语义违规会构成"基线上升"，被 M-2 的"只降不升"规则拒绝——门禁就永远装不上。独立维度让"引入一个守卫"是**该维度的一次性 bootstrap**（U8 规则），而该维度**此后同样只降不升**。

### 4.2 判定流程（完全复用 M-2 三条断言）

```
collect_violations(source)          # ruff + SEM 合并成统一违规流
  ↓ 按 code 前缀分流维度
每维度独立执行：
  A1 净增长   current(file,rule) ≤ baseline(file,rule)
  A2 新增行   added_lines_viol(file,rule) ≤ baseline(file,rule)
  A3 基线完整性 baseline.total ≥ 实测 且 增长审批未过期
  ↓
任一维度失败 → 退出码 1，CI 红
```

SEM 码参与 A2 的判定方式与 ruff 码完全一致：**新增行上的 SEM 违规同样受配额约束**（干净文件零容忍，脏文件额度用于重写存量脏行）。

## 5. 29 条历史遗留问题的下降趋势：怎么统计与追踪

### 5.1 先厘清一个容易混淆的点

**"29 条台账问题" ≠ "29 个代码点"。**

- **台账层** 29 条 = 29 个*主题聚合*（如 KI-SILENT-001 一条覆盖 `scripts/**` 全目录）；
- **代码层** 同一主题展开成**几十到几百个具体违规点**（SEM002 的 349 条就分布在 100+ 文件）。

所以"29 条开始净下降"必须**分两层看**，否则会出现"改了一个文件，29 条纹丝不动"的错觉。

### 5.2 三个度量层次

| 层 | 指标 | 含义 | 当前值 | 目标 |
|---|---|---|---|---|
| **L1 台账层** | `guard == NONE` 的条目数 | 还有多少问题**没有自动守卫**（会复发）| **29 → 21**（8 条已被守卫接管）| 0 |
| **L1b 接管映射** | 每条被接管条目对应的代码点数 | 台账条目 ↔ 具体代码点的对应关系 | 见 §5.4 | 逐条归零 |
| **L2 代码层** | 语义债务池 SEM001/2/3 总量 | 实际待修的代码点数 | 570（213 / 349 / 8）| 持续下降 |
| | ruff 债务池总量 | 通用规则的存量 | 252 | 持续下降 |
| **L3 维度层** | 两份基线的额度总数 | 门禁实际承认的存量 | 252 + 570 | 与 L2 同步下降 |

### 5.3 追踪机制

`scripts/quality_trend.py` 每天生成一个快照到 `data/quality/trend_YYYYMMDD.json`：

```json
{
  "date": "2026-11-01",
  "ledger": {"total": 37, "no_guard": 21, "guarded": 16, "still_present": 35,
             "no_guard_ids": ["KI-COMPETE-001", "..."]},
  "semantic_pool": {"total": 570, "by_rule": {"SEM001": 213, "SEM002": 349, "SEM003": 8}},
  "ruff_pool": {"total": 252},
  "baselines": {"ruff": 252, "semantic": 570},
  "coverage": {"KI-ATOMIC-001": {"rule": "SEM001", "scope": "...", "hits": 11}}
}
```

`report` 子命令把当前值与**上一次快照**对比，输出差值与净变化：

```
【与上次快照的差值】
  语义债务池     580 → 570   ↓ -10
  ruff 债务池    252 → 252   ＝ 0
  台账无守卫条数  29 → 21    ↓ -8
  台账仍复现条数  35 → 35    ＝ 0
  → 净变化 -18（负数 = 净下降，正数 = 净增长）
```

### 5.5 下降曲线怎么用（周会口径）

| 周期 | 看什么 | 判据 |
|---|---|---|
| 每日 | 语义债务池总量 | 是否 ≤ 昨日（**只允许持平或下降**，上升说明有人绕过门禁）|
| 每周 | L1 无守卫条数 | 21 → 0 的路线图（哪些条目还没守卫、能否人工补）|
| 每周 | 每条被接管条目的代码点数 | 哪条在推进、哪条卡住 |
| 里程碑 | 语义债务池 < 300 | 可把 SEM002 从"基线额度"升级为"全量阻断"（届时基线即可清零）|

### 5.6 与"29 条里剩下的 21 条"的关系（重要边界）

三条 AST 守卫**只能覆盖语义类问题**。剩下 21 条无守卫问题里：

- **仍可由 AST 覆盖**：KI-COMPETE-001/002（并发顺序，需 systemd 依赖分析）、KI-MCP-002/003（契约校验 / 路径穿越，需参数校验守卫）；
- **必须人工或专门工具**：KI-OPS-001~003（运维脚本）、KI-SKILL-001/002（技能运行时）、KI-PERF-002/003（性能）、KI-SIZE-001 / KI-IMPORT-001（代码体积）、KI-DOC-001~003（文档一致性）、KI-MAKE-001/002（Make 口径）、KI-EXEC-001（归档）。

**所以"29 条全部靠这三条守卫自动下降"是不成立的**。准确说法是：

1. 三条守卫把其中 **8 条**从"无守卫（会复发）"迁到"有守卫"（29 → 21）；
2. 为整个语义类问题建立了**可量化、可逐日下降**的债务池（570 个代码点）；
3. 门禁从"只拦新增行违规"扩展到"**新增行不得引入新语义违规**"——增量侧已经封死，存量侧开始净下降。

剩余 21 条需要各自的专门守卫或人工修复，其中约 10 条可在下一轮（M-5 修复必带测试 + M-6 门禁纯化）顺带解决。
