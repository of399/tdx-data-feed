## 2. 为什么名单变了而分母不变（结构判据）

`quantify` 的宇宙**不来自名单**：

- `scripts/audit_daban_st_tier_pollution.py:460 _pick()` → `:199 _daily_iter()` → `tdxfeed.paths.daily_files()`，
  排除指数用 `tdxfeed.symbols.INDICES` 现算（`_index_symbols`）。名单不在入参链上。
- 名单唯一的进入点是 `:392 _scan()` 里的 `uni = load_universe()` / `st_now = {c for c, n in uni.items() if is_st_name(n)}`
  （`:402-403`），它只当**分组键**用：`by_exch` 的 ST/非 ST 两行，以及并轨日「同步解锁」自校验的
  `release_st` / `release_ctl`。行数、现役 y=1、5% 档天数、翻转都不经过它。

实测这三件事（只读探针 `票数 = pool − short_history`）：

```
pool（daily_files 枚举、排除指数、板块 main+gem）= 5,229 只     ← 名单刷新前后同一个数
行数 < MIN_ROWS=30 被 _series 跳过 = 7 只 ⇒ 票数 = 5,222        RC=0
主动排除（不参与任何计数）: {'index_symbol': 8}
```

- 新增 362 只里**真能进 pool 的只有 7 只**（沪深新股 001246/001381/301569/301660/301686/301716/301718），
  而它们现在全在 7 只 `short_history` 里 ⇒ **对样本行的贡献是 0**；其余 355 只是北交所 `920` 段，
  `data/parquet/daily` 里没有日线，连文件都点不到。
- 被删掉的 4 只（000016 / 301139 / 601059 / 601198）**仍然在 pool 里**——pool 由日线目录决定，
  名单少了它们不影响扫描 ⇒ 分母不会因为"退市票离开名单"而缩小。

**票数那个 +1 的来源不是名单**，这一点单独钉死（探针：对 pool 全表只读 parquet 页脚行数）：

```
全池里恰好 30 行的文件只有 1 个：sh601091（30 行，首根 2026-09-17）   ← 旧名单在场 = 是，新名单在场 = 是
紧邻的那只 688837 是 31 行                                            ← 两侧都在场
short_history 计数：11-05 = 8（该文档 :695，sensitivity 三趟 ×8=24）→ 11-06 = 7（本轮 quantify；sensitivity=21=3×7）
```

⇒ `short_history` 少 1 与票数多 1 逐一对上，而跨过 `MIN_ROWS=30` 的那只票**本来就在旧名单里**：
这 +1 完全由"日线自己长了一根"造成，与名单刷新无关。基准率/放大率那 −0.01pp 也全来自
分母 +5,234 行（一个新交易日 × 约 5.2 千只票）而分子恒为 52,919。

⇒ 因此那句话要写到字面：**`52,919 / +24.42% / [16.32%, 36.68%] / 16,763,761 / 216,739` 这几个数是
「2026-11-05 的日线快照 + 名单 5,221 宇宙」上的读数；引用时必须同时标日期与宇宙版本。** 中心档翻转
在两个宇宙版本上同值（52,919），但**分母类读数随日线目录逐日变**，与名单无关。

名单确实改变的那一格也实测出来了（它属于自校验，不属于污染量）：

```
当前名 ST 的主板票（观察数）：11-05 = 144 只 → 11-06 = 142 只（解除 8 只，5.6%）
当前非 ST 的主板票（观察数）：11-05 = 3,041 只 → 11-06 = 3,043 只（解除 2 只，0.1%）
```

即 `docs/research/2026-11-05-daban-st-tier-label-pollution.md:580-584` 那两句（「ST 组解锁率是对照组
**84 倍**」= `(8/144)/(2/3,041)`）里的分组随名单刷新从 144/3,041 变成 142/3,043 ⇒ 同一判据今天读作
`(8/142)/(2/3,043) ≈ 85.7 倍`。**比值方向和量级不变，但两个分母是名单侧的数，引用时要认日期。**
（注意别拿 `cmd_rule` 那句「主板非 ST=3,053」来对：那是未过"观察"闸的全数，属另一个口径。）

## 4. 旧名单落后多久（`due` 的实测依据）

不能用"感觉"给 deadline，这里有一个可核验的下限：

```
001246 首根日线 2026-09-30（22 行）   ← 它上市 37 天后仍不在名单里
301686 首根 2026-09-22（27 行）   301716 首根 2026-09-29（23 行）
301569 首根 2026-10-15（16 行）   301660 首根 2026-10-13（18 行）   301718 首根 2026-10-22（11 行）
```

同一批日线文件的末根全是 **2026-11-05** ⇒ 日线同步在正常跑，**只有名单停在 ≤2026-09-30 的状态**，
落后 ≥37 个自然日。这 37 天里沉淀出来的就是本轮一次性清掉的账：7 只新股、4 只退市、31 条改名
（19 条 `XD`/`C` 标记消退 + 9 条 ST/退市标记变化 + 3 条换名）、名称侧与面板的 11 只对称差。

## 5. 落下来的判据

- `tests/test_universe_writer.py` — 写入者唯一且在场、`names.py` 的生产者声明可核验、源不可用不得写成
  「名单没变」、闸门拒写不动原文件、原子写必须走 `tdxfeed/atomic.py`。
- `tests/test_universe_path_single_source.py` R6 — 给写入者的**形状级**豁免（只允许 `read_bytes()` 取旧字节
  做备份与 no-op 判据）；同文件出现 `read_text()`/`open()`/`json.loads` 照判红；登记腐化照判红。
- `tests/test_universe_daily_parity.py` — 双向差逐只落在登记表：**920 段按「段」放行（新股不会让它红），
  日线侧按「码」闭合登记（新退市票会让它红，逼一次人工判断）**；另加三条卫生判据（理由非占位、豁免不吃非 920 段、
  段豁免不得是空前缀）。变异对照三条各自跑过：清空一条登记理由 ⇒ 红、登记表少登记一只 ⇒ 红、
  把 `UNIVERSE_ONLY_PREFIX` 改成 `""` ⇒ 红。**最后那条是本轮做变异时才发现的坑**：`startswith("")` 恒真，
  想「收紧」空前缀反而把 355 只全免检（真数据三读数：`920`⇒0 / 不匹配的段⇒355 / `""`⇒0）。
- `config/known_issues.yaml` 新条目 **KI-OPS-008**（`detect: glob_absent` 判「`systemd/` 下没有 universe
  刷新单元 ⇒ 未修」，`guard: tests/test_universe_writer.py`，`status: OPEN`，`due: 2026-11-20`，依据是 §4 的「名单落后 ≥37 个自然日」实测）。

## 6. 这一修**不**治什么

1. **名单仍然没有调度**（KI-OPS-008 记的就是这一格）：本轮之后如果不装 timer，37 天后同样的沉淀会重来。
2. 北交所 920 段的**日线**依旧不在场（2026-10-21 下线）⇒ 名单收了它们但任何按日线取数的链都点不到，
   这不是坏数，是已知形状；要治得单独授权恢复 bj 日线。
3. 现役 `data/double_up/d_signal_5d_model_daban.txt` 未换（mtime 仍 2026-10-19 17:30:31），
   `MODEL_REGISTRY` 未加条目，`scripts/predict.py:466` 的推理侧 `is_st=` 接线仍未做（KI-DATA-008 那格）。
4. 本文不改 §1 的翻转数与区间结论；它改的是**引用规则**（日期 + 宇宙版本必须一起标）。
