## 1. 适用同步策略

| 策略 | 描述 | 适用条件 | 风险 |
|---|---|---|---|
| **A. 保持单向**（推荐默认） | 仅 repo → vault，vault 为只读消费副本 | 研究笔记仍在仓库内写，或偶尔手动导出 | 最低 |
| **B. 分区双向** | 仅允许 `09-研究笔记/` 等指定目录回写，排除所有生成物（MOC/archive/带 frontmatter 的副本） | 用户确实要在 Obsidian 内写笔记 | 中（需严格隔离） |
| **C. 三路快照协调** | 维护 `.sync-state.json`（file→hash+mtime）做 base/repo/vault 三方比对 | 任意双向场景的必备底座 | 低（工程量大） |
| **D. 写回自动提交/提 PR** | vault 回写后自动 `git commit`（或开 PR） | 需要可追溯回写 | 中（误提交风险） |
| **E. 外部多端同步**（Obsidian Sync/云盘） | 把 vault 当作多写者 | 跨设备写笔记 | 高（超出本脚本能力） |

**推荐组合**：若确需双向，采用 **B + C + D**——隔离目录 + 快照协调 + 自动提交，并**显式排除生成物**以防回写循环。

## 2. 冲突检测与解决

- **检测**：以 `.sync-state.json` 记录上次同步时各文件 hash 为 base。每轮同步计算 repo 侧 hash（R）与 vault 侧 hash（V）：
  - R==base、V!=base → vault 改，**回写**；
  - R!=base、V==base → repo 改，**下发**；
  - R!=base 且 V!=base → **冲突**，进入隔离目录（如 `99-冲突待处理/`）等待人工裁决，不自动覆盖。
- **解决策略**：
  - 默认 **LWW（按 mtime 胜出）** 仅用于"非冲突"单向流动；
  - 真冲突**不自动合并**（Markdown 结构化合并不可靠），统一进冲突隔离区 + 写日志。
- **前置**：必须区分"生成文件"与" authored 文件"，否则 base 基准失真。

## 3. 数据一致性

- **单一事实源**：当前约定仓库为事实源。双向会**削弱**该约束——必须在回写前确认哪些 vault 内容"受权威"。
- **循环写防护**：`00-知识库入口/索引-MOC.md`（脚本生成）、`08-报告/archive/*`（脚本派生）、frontmatter 富化副本**必须列入回写排除列表**，否则会回流仓库造成覆盖/抖动。
- **幂等性**：同态重跑须产出相同结果（当前 `cp` 覆盖 + 归档按 hash 去重已具备幂等性；增加写回后仍须保证）。
- **一致性校验**：每轮结束校验 `.sync-state.json` 与两侧实际 hash 一致（允许"仅 vault 侧新增未提交"这一已知偏差）。

## 4. 延迟与吞吐

| 环节 | 当前/预估 | 说明 |
|---|---:|---|
| 事件检测延迟 | 亚秒级 | systemd path 内核 inotify 触发 |
| 单向脚本耗时 | ~1–2s（22 篇） | 纯 `cp` + 少量 Python |
| 双向扫描耗时 | 线性于文件数 | hash 全部 vault 文件，数十篇量级可忽略；>1k 篇需分目录 |
| 回写提交耗时 | 主要瓶颈 | `git commit`/PR 网络 IO；建议批量合并、加 cooldown |
| 抖动 | 路径单元无 debounce | 连续保存会触发多次同步 → 需脚本内 `flock` + 最小间隔（如 5s） |

> 规模结论：当前 vault 量级（数十篇）下，双向同步的延迟/吞吐**不构成瓶颈**；真正的成本在"策略与隔离的正确性"，而非性能。

## 5. 故障恢复

- **原子写**：引入 `temp + rename`，避免中断留下半截文件（当前 `cp` 不具备）。
- **运行锁**：`flock` 防并发重入；上次未完成则跳过或排队。
- **幂等重跑**：任意中断后再次触发，应能从 `.sync-state.json` 继续协调，不产生重复/丢失。
- **回写失败回滚**：vault→repo 写回若 `git commit` 失败，须保留 vault 原文、不更新 base，下一轮重试。
- **快照兜底**：`.sync-state.json` 本身损坏时，降级为"全量三路比对"（代价是误报冲突，但安全）。

## 6. 边界场景

| 场景 | 行为 | 缓解 |
|---|---|---|
| 并发写入（repo 与 vault 同文件） | 检测为冲突 → 进隔离区 | 三路比对 + flock |
| 连续快速保存 | 多次触发 | 脚本 `flock` + 最小间隔 debounce |
| 网络中断 | 本同步是**本地**文件↔本地仓库，不受影响；仅 `obsidian-git` 远程 push 受影响 | 核心同步解耦网络 |
| 部分节点离线（vault 在云盘/多设备） | 出现外部多写者，超出本脚本检测范围 | 禁止对 vault 启用 Obsidian Sync；或仅允许单设备写 |
| 脚本中途崩溃 | 可能留半截文件 / base 未更新 | 原子写 + 幂等重跑 |
| 仓库端有人直接改同文件并 push | 与 vault 回写竞争 | 回写前 `git pull --rebase` 或冲突隔离 |

## ⚠️ 已知限制与风险

1. **Markdown 结构化合并不可靠**：文本级 LWW 可能丢段落，冲突只能人工裁决。
2. **削弱单一事实源**：双向增加 repo/vault 漂移概率，需严格隔离与纪律。
3. **路径单元无 debounce**：连续保存放大同步次数，须脚本层兜底。
4. **外部多写者不可见**：若 vault 经 Obsidian Sync/云盘跨设备，脚本无法检测外部冲突。
5. **回写误提交**：自动 commit 可能把草稿/敏感内容推入仓库，需明确策略。
6. **`obsidian-git` 误配置**：若把 vault 当源码仓并 push 到公开远程，可能泄露（vault 与 repo 分离，风险低但需确认）。
