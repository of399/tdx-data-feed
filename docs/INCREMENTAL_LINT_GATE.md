# 增量阻断门禁（M-2）：新增行不得引入新违规 + 存量基线只降不升

（2026-11-01 落地 · 工具 `scripts/ci_violation_gate.py` · 基线 `config/ruff_baseline.json` · CI `.github/workflows/lint.yml`）

## 0. 为什么做这件事

现状：CI 只阻断 **4 类 ruff 规则**（E9/F63/F7/F82 = 语法错误与未定义名），完整规则集的 **252 条存量违规** 全部 `continue-on-error`（仅报告）。后果：

- 存量堵住了"把完整规则集改成阻断"的可能——**252 条历史债会立刻让 CI 全红**；
- 于是只能"全放行"，**新代码可以合法复制旧模式**（目录级 BLE001 豁免就是活例子）；
- 门禁只能防止"代码变坏"，**不能防止"债务增长"**。

本机制的作用：**用基线把 252 条存量冻结成额度**，从而在不还债的前提下，把完整规则集变成**增量阻断**——存量不阻断、增量必阻断，债务曲线由"上升"转为"平"。

## 1. 判定单位与核心概念

| 概念 | 定义 |
|---|---|
| **违规（violation）** | `ruff check . --output-format=json` 的一条输出：`file` + `row` + `col` + `code` |
| **配额单元** | **(文件 × 规则)**，例如 `scripts/predict.py` × `E402` |
| **基线额度** | 基线快照中该 (文件,规则) 记录的违规条数 = "已付过债的额度" |
| **新增行** | `git diff -U0 <base>...HEAD` 中新增/修改的行号集合（按文件） |
| **实测计数** | 当前工作树实测的该 (文件,规则) 违规条数 |

> 为什么用 (文件×规则) 而不是"规则"或"文件"？
> - 只按**规则**聚合：某文件新增一条 E402，若别处少一条则看不出来 → 太粗；
> - 只按**文件**聚合：新文件完全没有额度 → 任何违规都算新增（对），但老文件新增 E402 会被同文件其他规则的额度掩盖 → 太粗；
> - **(文件×规则)** 是能同时做到"新文件零容忍""老文件按规则分别记账"的最小粒度。

## 2. 三条断言与触发条件

| 断言 | 触发条件 | 判定式 | 失败含义 |
|---|---|---|---|
| **A1 净增长** | 每次 `check` 都跑 | `current(file,rule) ≤ baseline(file,rule)` | 该格违规数上升 = 净新增违规 |
| **A2 新增行** | 能取得 diff（`--base` 可解析）时跑 | `added_lines_violations(file,rule) ≤ baseline(file,rule)` | 新增/修改行上引入了该 (文件,规则) 的新违规 |
| **A3 基线完整性** | 每次 `check` 都跑 | `baseline.total ≥ measured_total` **且** 增长审批未过期 | 基线被抬高/低于实测；或 `growth_approved` 已过期 |

### 2.1 A1 与 A2 的分工（为什么需要两条）

| 场景 | A1 | A2 | 结果 |
|---|---|---|---|
| 干净文件新增 1 条违规 | 0 → 1 ❌ | 0 额度 < 1 ❌ | 双双拦住 |
| 脏文件新增 1 条违规（该格额度 3）| 3 → 4 ❌ | 1 ≤ 3 ✅ | **A1 拦住** |
| 脏文件重写存量脏行（违规数不变）| 持平 ✅ | 新增行违规 1 ≤ 额度 3 ✅ | 放行（允许动脏行）|
| 删掉 2 条旧违规、新增 1 条 | 3 → 2 ✅ | 1 ≤ 3 ✅ | 放行（总量在降）|

**结论**：A1 管"净增长"（存量只降不升），A2 管"干净文件不得被弄脏 + 额度用于重写存量脏行"。两条合起来实现"新增行不得引入新违规"的可执行版本。

### 2.2 触发条件（CI 里的实际行为）

| 事件 | A1 | A2 | A3 | 说明 |
|---|---|---|---|---|
| PR（`pull_request`）| ✅ | ✅（base=`origin/main`）| ✅ | 三条全跑 |
| push 到 main | ✅ | ❌（base 与 HEAD 相同，无 diff）| ✅ | 只跑基线断言 |
| 本地 `make lint-gate-local` | ✅ | ❌（`--no-diff`）| ✅ | 只跑基线断言 |
| diff 基准不可用（无 `origin/main`）| ✅ | ⚠️ 跳过并告警 | ✅ | 工具明确打印"跳过 A2"，不静默 |

## 3. 基线快照的更新与校验规则

### 3.1 文件格式（`config/ruff_baseline.json`）

```json
{
  "version": 1,
  "created": "2026-11-01",
  "updated": "2026-11-01",
  "measured_at": "dab26a8",
  "ruff_version": "ruff 0.16.7",
  "total": 252,
  "files": 82,
  "by_rule": {"E702": 44, "B905": 27},
  "by_file_rule": {"scripts/predict.py": {"E402": 1, "SIM115": 2}},
  "growth_approved": {                       // 可选：仅在获批上升时存在
    "reason": "紧急修复引入的临时豁免",
    "approved_at": "2026-11-01",
    "expires": "2026-12-01",
    "grew": [{"file": "...", "rule": "E402", "from": 1, "to": 2}]
  }
}
```

### 3.2 更新规则（`make lint-baseline` / `update`）

| 规则 | 内容 |
|---|---|
| **U1 只降不升** | `update` 默认**拒绝**任何 (文件,规则) 计数上升；只有"收紧"与"持平"会被写入 |
| **U2 拒绝时给出清单** | 拒绝时打印全部上升格（文件·规则：旧→新），并给出三条处理路径 |
| **U3 上升需显式审批** | 必须 `--allow-growth --reason "..."`；缺 `--reason` 直接退出码 2 |
| **U4 审批带到期日** | 上升时写入 `growth_approved`，`expires = 今天 + 30 天`；记录 `reason` / `approved_at` / 逐格 `grew` 清单 |
| **U5 到期即失败** | `expires` 早于当天 ⇒ A3 失败，CI 红 ⇒ 30 天内必须复审或偿还 |
| **U6 记录测量点** | 每次更新写入 `measured_at`（当时 HEAD）与 `ruff_version`，便于追溯基线来源 |
| **U7 版本漂移提示** | `check` 时若当前 ruff 版本 ≠ 基线记录的版本，打印告警（规则集可能变化，建议重测基线）|
| **U8 初始创建例外** | 基线文件不存在时按当前实测**创建**初始基线（这是唯一允许"从 0 到 N"的入口）|

### 3.3 校验规则（CI 每次 `check` 都跑）

| 校验 | 条件 | 失败含义 |
|---|---|---|
| **V1 基线不得低于实测** | `baseline.total ≥ measured_total` | 存在未登记的新违规（或基线被下调作弊）|
| **V2 逐格不得低于实测** | A1 覆盖 | 某格净增长 |
| **V3 审批不得过期** | `growth_approved.expires ≥ 今天` | 临时豁免到期未还 |
| **V4 结构合法** | `tests/test_ci_violation_gate.py` 校验字段完整、`total` 与 `by_file_rule` 自洽、计数 ≥ 1 | 基线文件被写坏 |
| **V5 守卫存在** | 同上：`status=FIXED` 的台账条目必须指向真实存在的 guard 文件 | 修了但没留守卫（会复发）|

## 4. 结果判定方式

### 4.1 退出码

| 码 | 含义 | CI 行为 |
|---|---|---|
| **0** | 全部断言通过 | 继续后续步骤 |
| **1** | 断言失败（A1/A2/A3）| **该 job 失败**，PR 不得合并 |
| **2** | 工具错误（ruff 执行失败 / JSON 解析失败 / `--allow-growth` 缺 reason）| job 失败（区别于"代码有问题"）|

### 4.2 输出判读

```
实测违规 254 条（83 文件 / 31 规则） · 基线 252 条
diff 基准 HEAD~1：1 个文件有新增行，其中 2 条违规落在新增行上
断言：A1 净增长 2 失败 · A2 新增行 2 失败 · A3 基线完整性 1 失败

❌ 失败 5 项：
  [A1 净增长] scripts/_gate_probe_demo.py · F401 · 基线 0 → 当前 1 (+1) 存量只降不升：此格违规数上升
  [A2 新增行] scripts/_gate_probe_demo.py · F401 · 基线 0 → 当前 1 (+1) 新增行违规于 L1
  [A3 基线完整性] (全仓) · (总量) · 基线 252 → 当前 254 (+2) 基线低于实测：存在未登记的新违规
```

每条失败都带 **(文件 · 规则 · 基线值 → 当前值 · 增量 · 证据行号)**，可直接定位。

### 4.3 失败后的处理路径（门禁自己会打印）

1. **优先就地修掉新增违规**（多数是分钟级：补 import 顺序、去多余 f 前缀、改 `except Exception`）；
2. 确属历史遗留且本次无法修：把违规挪到**未改动的行**，或执行 `make lint-baseline` 按实测收紧基线（只降不升）；
3. 需要临时豁免：`update --allow-growth --reason` 写入 **30 天有效期**的审批，到期未还 CI 自动变红。

## 6. 与其它机制的关系

| 机制 | 关系 |
|---|---|
| `config/known_issues.yaml`（台账）| 台账管**具体问题**的登记与复发统计；本门禁管**通用规则**的增量约束 |
| 台账 `guard` 字段 | 台账条目修完必须绑守卫；本门禁正是"守卫"的一种实现形态（自动扫描）|
| M-3 豁免行级化 | 本门禁落地后，BLE001 的目录级豁免可逐步换成行内 noqa——**新增行的 noqa 不再被豁免**，由 A2 兜底 |
| M-4 AST 语义守卫 | 本门禁只覆盖 ruff 规则；并发/原子写/超时等语义类仍需 AST 守卫补齐 |
| `make ci` | `ci` 目标是 `lint format test canary`；**本门禁是独立 job**（`lint.yml`），不依赖宿主 systemd |

## 7. 已知边界

1. **ruff 版本敏感**：规则集在版本间会变，基线与实测不可比时输出会提示（U7），但**不自动阻断**——避免因升级 ruff 而红一片。
2. **A2 依赖 diff 可得**：PR 场景成立；push 到 main 时自动跳过（此时只剩基线断言）。
3. **`_archive/` 等目录仍计入**：ruff.toml 的 `extend-exclude` 未覆盖 `_archive/`，其中 13 条违规占用了额度；若决定归档，应同步加入 exclude 并重测基线。
4. **只覆盖 ruff 规则**：语义类问题（并发、原子写、超时、口径漂移）**不在本门禁覆盖范围**，需靠台账 + M-4 的 AST 守卫。
5. **额度不是许可证**：A2 的额度允许在脏行上重写，但**不允许把额度用完再添**；A1 仍会拦总量增长。
