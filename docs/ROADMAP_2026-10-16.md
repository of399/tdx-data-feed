## 路线 1：v7r → v9 量化系统迭代

### 目标
PnL Huber + akshare SW 组合作为 v9 模型替换 v8；决策前先回测，对比 v7r / v8 / PnL+SW 三者的 OOS Sp（out-of-sample Spearman）。

### ⚠️ 当前进展（2026-10-16 重要更新）
v9 **已尝试部署**但暴露**致命 bug**：预测极度偏斜——94%+ 概率无脑说"涨"，方向判别完全退化（泛化差、对实盘无效）。

**根因（数据/任务错配）**：
- 之前 v9 训练用的是 `tdx_v4_train`（**描述性历史文本**，如"今日涨…"类）——"涨"占比 93.9%（极端失衡）
- 正确的数据集是 `data/v4fwd`（**前瞻 5 日方向标签**）——**类别平衡**：涨 33.8% / 跌 39.8% / 震荡 26.4%
- 模型走捷径：永远说"涨" → 训练 loss 漂亮，但方向判别完全退化

**已执行的修复动作**：
1. config 改 `dataset: tdx_v4fwd_train` / `eval_dataset: tdx_v4fwd_val` / `max_samples: 64056`
2. 清空旧 v4 checkpoint + adapter，**从 Qwen3-14B base 从零重训**（~30h）
3. **保留 `overwrite_output_dir: false`**：若遇宿主 SIGTERM，看门狗可从最新 v4fwd checkpoint 续训
4. v4fwd_val 分布偏跌（~56%）——**eval 仅作监控用**，不影响训练标签平衡
5. 首个 **checkpoint-200 落地后跑 `run_v4_eval` sanity** 验证方向判别是否真正改善

### 验收标准
- [ ] v4fwd 重训完成（~30h，从 base 训到收敛）
- [ ] checkpoint-200 → `run_v4_eval` 方向判别 sanity 通过（不再是 94% 偏涨）
- [ ] 三者 OOS Sp 数值产出（v7r / v8 / PnL+SW，数值表 + 对比图）
- [ ] 决策文档：基于 Sp + 业务可解释性选 v9 候选
- [ ] v9 部署到 Ollama 端点（如选用 LoRA 类）或 LightGBM 推理端（如 PnL Huber）
- [ ] v8 端点移除或降级为 fallback
- [ ] `predict.py` 默认推理模型切换

### 子任务（已根据 v4fwd 重训调整）
1.1 ✅ config 切到 `tdx_v4fwd_train/val`，`max_samples: 64056`
1.2 ✅ 清空旧 v4 checkpoint + adapter
1.3 🔄 重训 `qwen3-14b-tdx-v9`（**从 base 训**，~30h，看门狗 `scripts/v9_train_watchdog.sh` 监控）
1.4 ⏳ checkpoint-200 → `run_v4_eval` sanity（方向判别非偏斜）
1.5 ⏳ 并行：训练 `pnl_huber_v9`（35/33 维，Huber 损失 + 行业聚合）
1.6 ⏳ 在 OOS 测试集上回测三模型（v7r / v8 / PnL+SW），产出 Sp
1.7 ⏳ 对比 + 决策（v9 = max(Sp) 且业务可解释）
1.8 ⏳ 部署 v9 → `predict-daily.timer` 切换默认模型
1.9 ⏳ v8 端点保留为 fallback 30 天 → 移除

### 估计工时（已修正：v4fwd 重训拉长整体工期）
- v4fwd 重训: ~30h（从 base 训，含 SIGTERM 续训缓冲）
- PnL Huber v9: 1-2h
- 回测 + 对比: 2-3h
- 决策 + 部署: 1h
- **合计**: 32-37h（vs 原估 7-13h，**主要由 v4fwd 重训拉长**）

### 依赖
- GPU 资源（2×RTX 5060Ti 16G, Ollama 占满 96% → 训练期间 v7r 推理需降级或暂停）
- **v4fwd 数据已就位**（`data/v4fwd/`，前瞻 5 日方向标签，类别平衡）
- 续训坑仍适用：移走 `optimizer.pt/scheduler.pt/rng_state_*.pth` 全新优化器续训
- akshare SW 行业数据已就位（`akshare_industry_loader.py` → `data/industry/`）

### 触发条件
**已自动触发**（修复动作已执行，~30h 训练已启动）
- 路线 4 完成（已 ✅）
- v9 bug 修复（用户已批准立即重训）

### 风险（已更新）
- v5(r8) ↔ v6(r16) rank 不兼容（v8 fusion 失败案例）
- PnL Huber 33/35 维 R² 0.166→0.278（+67%），但 OOS Sp 可能不如 v7r（需实测）
- 训练时间受 GPU 抢占影响（Ollama v7r 常驻）
- **新增**：宿主疑似对 ML 进程发 SIGTERM（根因未明，非 OOM）—— 已设 `overwrite_output_dir: false` 让看门狗从最新 v4fwd checkpoint 续训
- **新增**：v4fwd_val 偏跌 56%——eval 仅监控；不影响训练（训练用 v4fwd_train 平衡分布）
- **新增**：若 v4fwd 重训后方向判别仍差 → 数据/任务定义需重新审计（不是单纯换数据集）
- **新增**：v4_train 与 v4fwd **不可混用**——前者描述性历史文本（93.9% 涨），后者前瞻方向标签（平衡）。训练前必须确认 `dataset_dir` 与任务定义对齐

## 方案 B：路线 1+2 并行执行清单（接 GO 后启动 · 2026-10-16 决策）

### 决策与理由
- **方案 B（不暂停，并行）**：v4fwd 重训（路线 1，~30h GPU）与 D→E 联调改造（路线 2，6-9h CPU/IO）在算力上**完全错峰**——GPU vs CPU/IO。
- **拒绝方案 A（暂停 v4fwd）**：暂停 v4fwd 引入 SIGTERM 续训 overhead + 看门狗协调 + 风险叠加，整体更慢。
- **唯一需要等 v4fwd 的环节**：PnL Huber 训练（~2h，需 GPU 释放）。
- **整体工期**：~33h（vs 方案 A ~32h，**且无暂停风险**）。

## 路线 2：量化方案 D→E 信号联调

### 目标
打破 D（预测）与 E（回测/实盘）独立运行的现状，**端到端联调**：
```
predict.py Top50 → plan_e_backtest 子集回测 → plan_e_journal 入库
```

### 验收标准
- [ ] `predict.py` 增加 `--emit-to-plan-e` 参数（输出 Top50 名单到 `data/signals/`）
- [ ] `plan_e_backtest.py` 增加 `--input-from-predict` 参数（消费外部信号列表）
- [ ] `plan_e_journal.py` 增加 `--from-predict-list` 模式（信号→入库）
- [ ] 端到端联调测试通过（用历史 predict 输出回测 + 入库全链路）
- [ ] 文档化联调使用方式（更新 `docs/PLAN_E_LIVE.md`）

### 子任务
2.1 `predict.py` 改造：增加 `--emit-top` 输出 csv/json 信号文件
2.2 `plan_e_backtest.py` 改造：支持 `--codes-file` 从外部 csv 读代码列表
2.3 `plan_e_journal.py` 改造：增加 `--signal-source predict_YYYYMMDD` 模式
2.4 联调集成测试：用 predict.py 历史输出 + plan_e_backtest + plan_e_journal 跑一遍
2.5 文档：更新 `PLAN_E_LIVE.md` 增加"信号驱动回测"章节

### 估计工时
- 代码改动: 4-6h
- 测试 + 文档: 2-3h
- **合计**: 6-9h

### 依赖
- v9 模型就位**前** vs **后**：
  - 前：使用当前默认 `vpnl_huber_stage1`（21 维 Polars）
  - 后：使用 v9（需等路线 1 完成）
- 路线 1 的决策结果（若影响 D 模型默认 → 需后置；否则可独立启动）

### 触发条件
- 路线 1 决策明确后（v9 部署会影响 D 模型默认）
- 或：使用当前 vpnl_huber_stage1 独立启动联调

### 风险
- predict.py 与 plan_e_backtest.py 现状耦合度低，参数改造可能需协调
- journal 入库需保持实盘/模拟分离（`journal.csv` vs `journal_sim.csv`）

- [ ] 告警规则：OOM / 卡死 / disk full / 推 pushplus-bridge（需先恢复）

- `canary-health.timer` 每 5min → `logs/canary.log`
