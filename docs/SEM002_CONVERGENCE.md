## 1. 统一改造模式

每处"未 raise、也无计数动作"的 `except` handler：

```python
# 文件头（模块级）
from collections import Counter

# 吞错计数（SEM002）：每处被吞掉的错误都计入统计，按函数名分桶，便于事后追溯失败率
_ERROR_COUNT = Counter()


def fetch_one(code):
    try:
        return _get(code)
    except Exception as e:            # 原来只有 logger.exception(e)
        _ERROR_COUNT['fetch_one'] += 1
        logger.exception(e)
```

| 规则 | 说明 |
|---|---|
| 计数插在 **handler 体第一行** | 无论后面走 `return` / `continue` / `break` 还是别的路径，都会计数 |
| 体只有 `pass` → 直接替换为计数语句 | 语义等价（都是 no-op），不改变控制流 |
| 计数键 = **所在函数名** | 定位"哪个函数在悄悄吞错"；模块级用 `<module>` |
| 每文件一个 `Counter` | `collections` 是标准库 → **零导入路径风险**（`scripts/` 下部分脚本没把仓库根放进 `sys.path`，引项目内模块会在某些调用方式下 ImportError）|

### 为什么不直接 `raise` 或 `return` 错误结构

349 处里 255 处是"返回错误结构/默认值"（例如 MCP server 返回 JSON-RPC error 对象、采集脚本回退到内置样例）。这类**错误已外传给调用方**，不是"静默消失"，强制改成 `raise` 会改变对外契约（尤其 MCP 协议响应）。因此统一选择"**外显 + 计数**"：错误仍然按原契约返回，同时留下一份可统计的失败计数。

### 3.3 为什么覆盖率没有明显上升（这很重要，别误读）

**改造往代码里加了 750 条新语句**（349 条计数 + 141 组"模块级计数器 + import" ≈ 400 条），而测试只执行到了其中一小部分：

- 净效果 = 新增覆盖（+260 行，其中 `scripts/` 贡献 +165）**抵消**了新增未覆盖语句（+490 行）→ 合计仅 +0.13pp；
- 四个包（tdxfeed / mcp / skill_router / quant）甚至**微降 0.3~0.4pp**——因为这些包的测试覆盖了主干逻辑，却很少触发"网络失败/解析失败"这类异常分支，新插的计数行自然落在未覆盖区。

**结论**：本次改造的目标不是提升覆盖率，而是**把不可观测的失败变成可观测的计数**。用"覆盖率"衡量它本身就是错配的指标。正确的验收指标是：
1. **SEM002 = 0**（增量侧封死）：✅
2. **计数确实会递增**（功能断言）：✅
3. **计数最终要被读到**（运营闭环）：❌ **尚未做** —— 见 §4.4 待办。

### 3.4 运营闭环：已补齐（汇总出口 + 落盘 + canary 维度 + 逐模块测试）

计数器最初是**每个模块的模块级变量**，没有任何读取方——统计口径是封闭的。本轮补齐了最后一段链路：

| 环节 | 实现 | 说明 |
|---|---|---|
| 汇总出口 | `tdxfeed/errors.py::snapshot()` | **零侵入**扫描已加载模块的 `_ERROR_COUNT`（不改那 141 个文件、不引入跨包导入风险）|
| 派生视图 | `totals()` / `summary()` | 按模块、按函数聚合 |
| 跨进程 | `flush()` / `read_recent()` | 生产入口用 `atexit` 登记 `flush`，把本进程计数追加进 `data/quality/swallowed_counts.jsonl`；canary 再按时间窗聚合回来 |
| 巡检维度 | canary 新增 **`swallowed_errors`** 维度（9 维中的第 9 个）| 读最近窗口（默认 24h，可环境变量覆盖）的吞错总数与集中点，超阈值 `warn` |
| 守卫 | `tests/test_error_counters.py`（288 个用例）| **逐模块**参数化断言计数键必须是真实函数名、模块级 Counter 导入、覆盖度下限；外加汇总出口行为与端到端（吞错 → 计数 → snapshot → 落盘 → 聚合）|

接入 `atexit` 落盘的生产入口：`scripts/predict.py`、`tdxfeed/full_sync.py`、`scripts/plan_e_journal.py`、`scripts/canary_health_check.py`、`scripts/daban_entry.py`。

### 3.5 收益表述（规范口径）

**本轮改造的真实收益表述为**：

> **存量 349 处失败从完全不可见变为代码中可见、可 grep、可统计。**

配套的两条边界，避免夸大：
- ✅ 可以说：新增的盲吞错会被 SEM002 门禁拦下；存量失败已全部计数并可按模块/函数检索；计数已进入 canary 巡检维度（可按窗口观察趋势）。
- ❌ 不说：**"失败率监控已上线"** —— 当前只统计**被吞掉的次数**，没有分母（没有"应该发生多少次"的口径），因此不构成失败率；且计数按进程退出落盘，窗口内的重复计数不构成去重口径。
